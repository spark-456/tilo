## 3. Notes

**Fonts and licences.** Every canvas loads the same Google Fonts stack: **Nunito** (weights 800/900, display/headings), **Nunito Sans** (400–800, body/UI), **JetBrains Mono** (500, 700 in the Player, Trace/mono). All three are Google Fonts under the **SIL Open Font License 1.1**, matching the PRD's "open-licence rounded sans + monospace" requirement (18.2). `Tilo 2 Balanced Refined.dc.html` additionally loads **Figtree** and **Fredoka** — these belong to unused alternate themes (`TH.crisp`, `TH.lively`) inside `tilo-kit.js` and do not render in any shipped screen text; the active theme (`balanced2`) uses Nunito/Nunito Sans/JetBrains Mono only. Figtree and Fredoka are also OFL-1.1 Google Fonts, so there is no licence risk even if left in, but they can be dropped as dead weight.

**Art medium.** All world/character/building art is **programmatically generated inline SVG** — `tilo-kit.js`, `tilo-world.js` and `tilo-player.js` build SVG element trees at runtime via a `React.createElement`-style `h()`/`E()` helper (isometric projection math, extruded boxes for buildings, path-based character rigs). There are no raster sprites, no canvas-element drawing, and no external icon font — icons are hand-coded SVG paths in each kit's `icon()` function. This is good news for the frontend build: the art is code, and can be ported directly into a React/SVG renderer without an asset pipeline.

**`support.js` is third-party and must not ship.** Its header reads: `// GENERATED from dc-runtime/src/*.ts — do not edit. Rebuild with 'cd dc-runtime && bun run build'.` It is Claude Design's own tool runtime (parses `<x-dc>` canvases, wires up React/ReactDOM for live-editing) — infrastructure for the design tool, not part of Tilo. `tilo-kit.js`, `tilo-world.js`, `tilo-player.js` and `worlds/k1-generator.js`, by contrast, are Tilo-specific and were clearly hand/AI-authored for this project — they are the closest thing to reusable renderer source the exports contain.

**`worlds/k1.events.json` — what it is and the HR-4 problem.** It is a `{world, version, events[]}` document: `world: "k1"`, `version: 1`, **409 events**. It is **not a recording of a real agent-harness run** — it is entirely produced by `worlds/k1-generator.js`, a deterministic script that hand-authors each event with an explicit timestamp and summary line (e.g. `E(6.8,'agent.spawned',{actor:'ivo',...})`), including scripted narrative beats ("Ivo is reading 212 rider interviews…") and several manually written **decision branches** (`branch({supplier:'switch'}, …)`, `{pricing:'grant'}` vs `{pricing:'decline'}`, `{motor:'allow'}` vs `{motor:'notnow'}`, `{share:'ops'}` vs `{share:'team'}`) that let the demo player replay the same world down different user-choice paths — something a real single recorded run could never do. Per PRD **HR-4** ("Replays carry a permanent 'Replay of run #… recorded [date]' banner"), if this data is ever presented as a "replay" in-product it needs to be clearly labelled as a **scripted demo fixture**, not a recorded run; no such banner or disclaimer exists anywhere in the current exports.

Event type breakdown (top): `agent.moved` 89, `building.planned` 45, `agent.working` 38, `building.constructing` 26, `building.operational` 26, `agent.spawned` 25, `district.created` 21, `building.archived` 13, `agent.handoff` 11, `data.transfer` 8, `app.refreshed` 8, `alert.raised` 7, `agent.retired` 7, `level.created` 6, `artifact.reviewed` 6, `memory.saved` 6, plus 25 further types at 5 or fewer occurrences.

**Event types in `k1.events.json` NOT in the PRD 9.5 registry:**
- `world.created` — the registry's `world` family only has `requested/planned/started/paused/resumed/completed/failed`, no `created`. This is the very first event in the file (`e001`), so the whole demo currently opens on an unregistered type.
- `user.joined` — no `user` family exists in 9.5 at all (a person "Anita M." looking at a building).
- `user.commented` — same missing `user` family (an inline comment on a building).
- `alert.batched` — the registry's `alert` family only has `raised/resolved`.

Per **HR-5** ("Unknown event types appear in the Trace only"), these four types should render in the Trace lens alone and have no world/HUD/Story effect — worth checking against `tilo-player.js`'s actual handling before reuse, since `world.created` currently drives camera/title effects in the generator's intent.

**`worlds/k1.layout.json` vs. the `WorldLayout` v1 contract (PRD 9.2).** The file predates the finalised contract: it has `{world, seed, tier, levels, islands}` at the top level, with no `v`, no `world_id`, no `theme`, and no top-level `semantic`/`geometry` split; gates live inline per-level (`levels[i].gates`) rather than in a top-level `semantic.gates` array with `between`/`policy_ref`; there is no `agents` array at all. A frontend builder should treat this as a legacy/reference shape to be migrated, not a drop-in fixture for the real contract.
