# Memory item rules beyond the schema (memory_item.schema.json 1.0.0, ADR-0049)

The schema checks one item, one body or one context block. The rules below also need the principal, the store, the
clock, the safety provider or the prompt that receives the notes. `MI-` is this file's prefix and the ids are stable.
"Code" means tilo-api, never a model. These notes are a new, person-written part of the PRD 13.1 Preferences layer;
they are not ADR-0030's closed preference facts (MEM30-d) and not FR-INT-05's `applied_preferences` (MI-10).

| Rule | Rule | Checked by | Source |
| --- | --- | --- | --- |
| MI-01 | **Whose.** `GET /v1/memory`, `POST /v1/memory`, `PATCH /v1/memory/{id}` and `DELETE /v1/memory/{id}` are the only routes. Owner and org come from the verified Principal, never from a path, query or body (the `create` and `update` schemas name neither). Every signed-in person owns their own list whatever their org role; no teammate, org owner, Approver or Team Lead reads, lists, counts or changes another person's, and no route takes a user id. An id that is not the principal's answers the same 404 `not_found` as an unknown id, before any other check. A demo session gets an in-memory list that is gone with the session, never the durable store. A request without a verified Principal answers 401 and touches nothing. | api | ADR-0049; PE-01 (same owner-only pattern) |
| MI-02 | **Writes.** `POST` with `create` answers 201 with the stored item: id minted, `created_at` = `updated_at` = server clock. A text equal to one of the person's stored texts after NFKC, trimming and casefolding answers 200 with that item and writes nothing (a double tap stores one). At 100 stored items a new `POST` answers 409 `memory_full` and writes nothing. `PATCH` with `update` changes only `text` and `kind`, sets `updated_at`, and answers 200; `source`, `id`, `owner`, `org_id` and `created_at` never change. `DELETE` answers 204 and removes the item at once (a hard delete: no tombstone, no soft-delete flag, no undo); the next prompt context no longer holds it. A body the schema or MI-03 refuses answers 422 with the field named and nothing written. `GET` answers `list`, newest `updated_at` first, ties by id. | api | ADR-0049 |
| MI-03 | **Text checks beyond the schema.** Code trims the text before the schema check. It refuses (422, field `text`) a text with any character of Unicode category Cc, Cf, Co, Cs, Zl or Zp, or any variation selector (U+FE00 to U+FE0F, U+E0100 to U+E01EF), astral ones included; a text the secret redactor would change (`secret_like`); and a text the safety provider flags (`flagged`). The text is screened once at each create and each text change, through the same `SafetyProvider` as a Quick question; a provider failure answers 503 with nothing written (fail closed). A refused text is never stored, logged or echoed. | api | FR-MEM-05, SEC-01, SEC-04 |
| MI-04 | **Suggest, never save.** Tilo never stores a note by itself: no model, sweep, run, triage, brief or connector writes one. A Quick answer may carry at most one `suggestion`, made by code from the person's own words in that question when it holds a phrase of `config/quick.yaml` `memory_triggers` (for example "remember that", "I prefer", "my manager is"): the sentence that holds the phrase, cut at 280 characters on a word boundary, with any "remember that" lead-in removed, and only if it passes the schema and MI-03's character and secret checks. Never text from a model's reply, mail, a document, a web page, a transcript, a calendar title or another person. A question that is only a memory instruction (it starts with a `memory_triggers.lead` phrase such as "remember") gets the suggestion and no model call. No answer text says a note was saved. The suggestion is stored only when the person taps it, which sends `POST` with `source: tilo_suggested`; dismissing it stores nothing and is not remembered. | api; web | ADR-0049; HR-1 |
| MI-05 | **Where notes are used.** Code builds `prompt_context` (the person's local `today`, and their notes newest `updated_at` first, ties by id, at most 20) and renders it as a fenced, labelled data block (`neutralise_marker`) in the user turn, never the system prompt (EFF-04), of exactly two calls: the person's own Quick ask, and the Director's brief extraction for intake that the person makes as world owner from a signed-in web or mobile-web session. Never for a call made for anyone else, an email or other unauthenticated intake, a run in a world the person does not own, a meeting room, the meeting bot, Autopilot, a draft to someone else, a tool, an event, a log line or a trace field. When the person has no notes the block renders as nothing and the prompt is byte-identical to the prompt without this feature, so recorded replays keep their keys (B-007). The Director may name a note it used in `brief.sources` (`kind: memory`, `ref`: the note's id); code keeps only ids from the block it sent and drops any other. A note in a run's prompt stays in that run's raw archive until the run or the person is erased; the list page says so. | api; harness tests | ADR-0049; FR-INT-05, EFF-04, FR-MEM-04, FR-MEM-09 |
| MI-06 | **Events.** A create and a change of text or kind each write one `memory.saved` (`layer: preferences`, `item_count: 1`) in the person's Desk world (PE-12): actor the person, target the person, `district` null, `vis: []`, `authz` null, and a `summary` that names no text (for example "You saved a note for Tilo."). A delete writes no event. The text never enters an event, log line, trace or metric. | api | PRD 9.5; PE-12, HR-1 |
| MI-07 | **Notes authorise nothing.** No policy, gate, risk tier, recipient, budget, Decision or consent reads a note, and a note never stands for a person's approval (PRD 10.4, HR-7). A name or address in a note is never a recipient: recipients come from the directory (PE-09) and every send keeps its gate. A plan or draft shaped by a note goes through the same gates as any other. | api; policy engine | PRD 10.4, HR-7, PE-09 |
| MI-08 | **Sharing follows the world.** A brief or plan the Director wrote with a note is part of that world: if the person later shares the world with a team (ADR-0040), the team sees the brief, not the note. The list page says notes shape the person's own tasks. No route or read model shows a note itself to anyone else. | api; web copy | ADR-0040; PE-31 |
| MI-09 | **Erasure and retention.** A note is kept until its owner deletes it or the person is erased; the erasure registry (FR-MEM-09) lists the memory store, and `verify_erasure` re-reads it. The only other copy is the note's retrieval chunks (`retrieval_chunk.schema.json`, RT-01), owner-only, replaced or deleted in the same request as the note (RT-07); no Memory Bank or other cache holds it. | api; erasure script | FR-MEM-09 |
| MI-10 | **Not FR-INT-05 facts.** Notes are free text the person wrote. They are not `tilo_planning.memory.MemoryLookup` entries and never fill `brief.applied_preferences` (whose citation names a closed field a code path set, ADR-0030). A later change that turns a note into a closed preference fact needs the person's own act on that fact and its own ADR. | api; planning tests | ADR-0030, FR-INT-05 |

## Fixtures

- `fixtures/memory_item/` exercises the stored item; `fixtures/memory_item.create/`, `memory_item.update/`,
  `memory_item.list/`, `memory_item.suggestion/` and `memory_item.prompt_context/` the bodies, the GET answer, the
  Quick suggestion and the prompt block. Invalid file names say the rule they break.
- MI-01 to MI-10 compare against the principal, the store, the clock or a prompt; they are the api and harness
  tests' (tickets M1 and M3 in ADR-0049), not fixtures.
