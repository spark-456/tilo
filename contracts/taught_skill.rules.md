# Taught skill rules beyond the schema (taught_skill.schema.json 1.2.0, ADR-0034, ADR-0037, ADR-0051)

ADR-0034 is **Accepted (overridable)**, 9 Oct 2026. ADR-0037 (TS-13 to TS-17, `real_run` and `run_answer`) was
accepted by the user on 12 Oct 2026. ADR-0051 (TS-18 to TS-21) was accepted by the owner on 16 Oct 2026. The schema checks one
record, result or event. The rules below also need the config, the team store, the ledger, other records or the
clock. `TS-` is this file's prefix, and the ids are stable. "Code" means tilo-api or the harness, never a model.

| Rule | Rule | Checked by | Source |
| --- | --- | --- | --- |
| TS-01 | **Who reads.** Everything goes through tilo-api for the verified principal. The owner reads and runs their own skill. For a `team` skill, the current members of `scope.team` (memberships re-read on every call, ADR-0015) can also read it, run it, try it and rate their own runs. Nobody else can. Another org's or another person's skill reads as absent (404, the same body as an unknown id). | api | FR-SKL-04, PE-01 |
| TS-02 | **Who writes.** Only the owner changes the name, scope, trigger, status, `paused`, `tool_access` or plan, makes fixes, or deletes the skill. A `team` scope names a team the owner currently belongs to. `owner` and `org_id` come from the principal, never from a request body. | api | FR-SKL-04 to 06 |
| TS-03 | **Capture.** Captured steps come only from the owner's own capture: typed words, an upload, a recording or Tilo's browser. Media goes through the ADR-0018 store into the owner's Desk world as an `upload` version: video/webm or video/mp4 (common 1.7.0), at most 50,000,000 bytes, inside the world's 200,000,000-byte cap, checked before any byte is stored. A `pinned` ref names a version in that scope. While capturing, nothing reaches a connector write or the outbox. Steps that the `skill_capture` role writes pass the secret redactor before they are stored. | api, memory | FR-SKL-01, AR-03, AR-04 |
| TS-04 | **must_ask is derived.** Code sets `must_ask` when the verb is send, post, pay, delete, share or book, or the tier of the step's action (`risk_tier` of the connector's action; an action that is not listed is T3) is T2 or T3. The runner works it out again from the current config before every run and step, and asks if either the stored or the current value says so. A model's "ask me first" suggestion is only the starting value of `ask_first` on the other steps. | api, harness | FR-SKL-02, PRD 8.3, 10.4 |
| TS-05 | **Who asks.** While a skill is `learning`, every step whose verb is not `read` stops to ask. While it is `trusted`, the steps with `ask_first` stop. In a real run an ask is a gate card (`approval.requested`, decided by a person). In a try run it is a question card, because nothing is authorised. `estimates.asks_per_run` counts the stops for the current status. A public post is T3 (`external_sharing`) and needs one approval for each post. | harness | FR-SKL-02, 03, 06; HR-7 |
| TS-06 | **Least privilege.** Each plan step's `tool` and `action` is an action of that connector in `config/connectors.yaml` or `config/mcp.yaml`, and the tool is in `tool_access`. At save, code sets each level to the lowest that permits the steps of that connector (`tilo_policy.access_levels.permits`). No level is above that, a connector that is not listed is off, and a run uses `effective_level(team, skill)`. | api, harness | FR-ACC-01, FR-ACC-02 |
| TS-07 | **Triggers.** A `schedule_id` names a schedule owned by the owner. An event trigger's `type` is registered and on `config/skills.yaml` `triggers.event_types`. Each filter key is a required data field whose schema is an enum or an id pattern, and it matches exactly. It fires only on events in worlds the owner owns, never on an event caused by a run of the same skill, never while the skill is a draft or paused, and at most `triggers.max_runs_per_day` times a day. | harness | FR-SKL-04 |
| TS-08 | **Trust.** `good_runs` is the number of the skill's finished runs (never try runs) that the person whose run it was rated `up`, each run once. Only the owner marks a skill `trusted`, and only while `good_runs` is at least `config/skills.yaml` `trust.good_runs`. The event records both values. Setting it back to `learning` is always allowed. | api | FR-SKL-06 |
| TS-09 | **Fixes.** Only the owner fixes, and only the skill's current version: `from_version` equals `version`, `to_version` is one more, and `step` is at most the plan's length. A fix sets the step's text and `ask_first` (never false on a `must_ask` step) and changes no tool, action or verb. A run keeps the version it started with, so the fix applies from the next run. The fix record and `skill.fixed` log it. | api | FR-SKL-05 |
| TS-10 | **Try runs.** A try run runs the skill's current version in the owner's Desk world, never while the skill is paused. Reads are real, at the `tool_access` levels. Each write goes to a dry-run outbox, which records an intent and has no dispatcher. A sign-in page or a CAPTCHA raises a needs-you card and stops the run (`needs_sign_in`, `captcha`); Tilo never types a password or solves one. The run stops at `config/skills.yaml` `try_run.max_credits`. `match` = `matched` / `total`; `matched` + `skipped` <= `total`, with equality when `completed`; `asked`, `intents` <= `total`. A writer that finds any dispatched side effect writes `alert.raised` and no result. Dev and CI use fake or replay providers (EFF-01). | harness | FR-SKL-03 |
| TS-11 | **Events.** The six `skill.*` types are written after their record write commits, in the acting person's Desk world. `actor` and `target` are that person, `district`, `level` and `item` are null, `vis` is `[]` and `authz` is null. `credits` and `trace` carry the `skill_capture` call or the try run's total. `data` holds ids, counts and enums only: no step text, note, name, file name, media, transcript or third party's words. | api, harness | HR-1, HR-7, PE-12 |
| TS-12 | **Helpers report.** It is served only while the org's opt-in is on. It is computed from fix records, rating records and `run_answer` records (TS-16) of the org's taught skills. `helpers` is sorted by user id and leaves out people with no answers and no fixes. `mistakes` counts thumbs-down ratings for the whole org. Nothing ranks, times or quotes a person. A month with no recorded source is reported as unavailable, never as zero. | api | FR-SKL-07, BQ-DSN-05, PRD 23.5 |
| TS-13 | **A real run is recorded when it starts.** Code writes the `real_run` in the same transaction that reads the skill: `org_id`, `skill`, `version` and `plan` come from that stored record, never from a request. The skill must be `learning` or `trusted` and not `paused` (a draft or a paused skill refuses, TS-06 and FR-SKL-06). `by` is the verified principal who started it: the owner, a current member of a `team` scope, or the owner for a schedule or event start. `world_id` and `run_id` are the world and run the harness made. A `run_id` is recorded once, and a second start with it writes nothing. A try run is never written here (TS-10). | api, harness | FR-SKL-05, FR-SKL-06, ADR-0037 |
| TS-14 | **A run finishes once, from its own world.** `finished_at` and `outcome` are written together, after the run's own committed terminal event for that `run_id`: `world.completed` gives `completed` and `world.failed` gives `failed`, and `finished_at` is that event's `ts`, never earlier than `started_at`. Pause all and the kill switch (`world.paused`) finish nothing: BQ-90 makes them final for the run, so that run stays unfinished and can never be rated. Nothing sets them from a rating, a request or a model. After that no field of the record changes, and a later fix changes neither `version` nor `plan`. | api, harness | FR-SKL-05, HR-1, ADR-0037 |
| TS-15 | **Who may rate which run.** A rating is accepted only when code reads a `real_run` of the same org and skill with the rating's `version` and `run_id`, `by` equal to the rater (a teammate rates their own run, never another's) and a non-null `outcome`. A thumbs up needs `completed`; a thumbs down is accepted on `completed` or `failed`. An unknown, foreign-org, other-version, unfinished or try run answers 404 with the same body as an unknown id. A run takes one rating, and a second one is refused with nothing written. `good_runs` (TS-08) counts the runs whose one rating is an up on a `completed` run. Fixture cases: `fixtures/taught_skill/crossref/`. | api | FR-SKL-05, FR-SKL-06, ADR-0037 |
| TS-16 | **Answers are linked, not copied.** When a question card answered by a person commits in a world and run that a `real_run` names, code writes one `run_answer` for (`skill`, `run_id`, `card_id`) with `version` and `world_id` from that `real_run`, and `by` and `at` from the card's recorded answerer and answer time (a Decision's `answered_by.ref` for a person, `answered_by.user` for a Team Lead, and its `at`). A gate, a consent card, a timeout default (`answered_by` default) and a repeat question answered from a Decision (`answered_by` decision) make none. A run that has no `real_run` makes none: history is never rebuilt from events. No question, option or answer text is copied. The run may be unfinished. The link is separate from the card record, which stays closed and channel-facing. Fixture cases: `fixtures/taught_skill/crossref/`. | api | FR-SKL-07, BQ-DSN-05, ADR-0037 |
| TS-17 | **Read and keep.** The owner reads every `real_run` and `run_answer` of their skill. Any other person reads only the records whose `by` is them (TS-01). A record is kept one year, as the ratings and fixes that cite it are, and goes with the skill and with the person (FR-MEM-09). History bars show only recorded runs and say so when there are none (HR-1). | api | FR-SKL-06, FR-MEM-09, ADR-0037 |
| TS-18 | **Browser hosts.** A plan step that browses uses connector `web`, action `browse_web` (declared with its adapter, ADR-0051 ticket B1); the record then names `hosts` (schema). Code proposes hosts only from what the person showed (hosts typed, or read off the recording or upload by the skill_capture role) and checks each against `browser.schema.json#/$defs/host`; the person sees them on the review screen and saves only the ones they keep. A run browses these hosts plus the ones typed in its request, nothing a page or a model adds (BR-02). | api; browser loop | FR-SKL-02, FR-CON-07, ADR-0051 |
| TS-19 | **Inputs.** `inputs` are named slots the run form or the request fills. A value is data handed to the run's units as delimited data, never an instruction, and a file input is a pinned artifact or a picked Drive file the person may read when the run starts (MN-02). A required input left empty stops the run before any model call with a needs-you card. | api | FR-SKL-04, ADR-0051 |
| TS-20 | **One understanding step for three ways of teaching.** describe (typed words), record (a recording made on the Skills page) and upload (a file the person brings) all go through `POST /v1/skills/captures` and then the skill_capture role (config/models.yaml, packages/providers only), which reads the words, the video frames, the narration when the person turned it on, and any attached document, as delimited data. Its output is a proposal in a closed response schema (steps, inputs, hosts); code then drops every step whose tool or action is not declared in config (listing it as "Tilo can't do this yet"), sets `must_ask` (the existing verb and tier rule), and keeps the draft until the person saves it. Nothing in a recording or text can add a tool, a host, a recipient or an approval. A recording with sound is accepted only when the role's profile has an `audio_input` price; otherwise it is refused before the model call, never sent unmetered. | api | FR-SKL-01, FR-SKL-02, PRD 16.3, ADR-0034, ADR-0051 |
| TS-21 | **Access is checked, not stored.** What a draft or saved skill still needs (a connector not connected, a level the team holds below what a step needs) is computed by code from the person's connections and the team's levels on every read and shown as "Needs setup"; it is never stored in the record, so a stale list cannot widen or narrow anything. `tool_access` stays the TS-06 least level, and a run re-checks every step against the current config and levels (TS-04). | api | FR-ACC-01, FR-ACC-02, ADR-0051 |
