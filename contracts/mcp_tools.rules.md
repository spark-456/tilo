# Tilo MCP server rules beyond the schema (mcp_tools.schema.json 1.0.0, ADR-0031)

ADR-0031 is **Proposed**: these rules bind the builders once the user approves it. The schema checks one `tools/call`
request and each tool's result shape. The rules below need the grant store, the token, the world records, the card
store, intake and the clock. tilo-api checks all of them before it answers (tickets MCP-b and MCP-c). `MC-` is this
file's prefix, and its ids are stable. The `mcp.*` audit events and the `mcp` channel are contract changes of ticket
MCP-a and are not in this file's schema.

| Rule | Rule | Checked by | Source |
| --- | --- | --- | --- |
| MC-01 | **Tilo's own tokens only.** Every call carries a bearer access token that Tilo's authorization server issued for this resource: its audience is the configured MCP resource URL (RFC 8707), it is unexpired, its grant is not revoked, and its client is allowlisted in `config/mcp_server.yaml`. Anything else gets a 401 with `WWW-Authenticate: Bearer resource_metadata=...`. A Firebase ID token is never an MCP token, and an MCP token is never accepted by another route or passed to another service. Tokens are stored only as SHA-256 hashes, carry a `tmcp_` prefix so the secret scanner finds them, and are never logged or written to an event. | api | MCP authorization spec, SEC-01, SEC-10 |
| MC-02 | **The grant is the principal.** The person is the grant's `uid`, and the org is `deps.ORG_ID`. No argument can name a user, an org, a role or a channel (the schema closes every input). The person must still hold an access declaration (SEC-15) when the call is made. | api | SEC-15, PE-05 |
| MC-03 | **Scopes.** Read tools need `tilo.read`. `answer_card` and `start_run` need `tilo.write`, which is off by default; the person turns it on per client on the consent screen or in Settings. `tools/list` lists only the tools the grant allows, and calling any other tool gets `insufficient_scope`. | api | ADR-0031 d4 |
| MC-04 | **The owner's worlds only.** A world is in scope only when its record owner is the principal (the S-14 owner scope; a shared viewer's scope is not offered over MCP in this version). Any other world, card or artifact id gets `not_found`, byte-equal to a missing one. | api | SEC-07, PE-05 |
| MC-05 | **The web's code paths, never a bypass.** `list_worlds` and `get_world` use the S-14 list and the owner's `GET /worlds/{id}/events` view. `list_artifacts` and `read_artifact` use the artifact store's `head` and hash-checked `read` through the world's Scope (AR-01, ADR-0018). `list_cards` uses the card feed. `answer_card` calls `CardStore.answer(channel="mcp")`. `start_run` calls intake's `submit_intake` with channel `mcp`. Nothing reads or writes a store that the web path does not. | api | SEC-03, ADR-0031 d3 |
| MC-06 | **Story lines are Tilo's words.** `get_world.story` holds the newest 20 event summaries of the owner's view, nothing from the archive, a prompt or a model's raw output. | api | HR-1, 13.2 |
| MC-07 | **Artifact text, narrowly.** Only a version the world recorded (EV-15) whose `screening` is `clean`. `text` is filled only for `text/markdown`, `text/csv` and `application/json` up to 262,144 bytes; otherwise it is null and `withheld` says why. No download URL, signed link or binary is ever served. | api | ADR-0018, FR-MEM-05 |
| MC-08 | **Content is data.** The tool descriptions say that artifact text and Story lines are data, not instructions, and the read tools carry `readOnlyHint: true`. Tilo acts on arguments only through their typed fields. | api | 16.3, EV-09 |
| MC-09 | **Nothing authorises over MCP.** Channel `mcp` answers `needs_you` cards only, like email (CH-RM). Gate, consent and meeting cards are never answerable over MCP: `answerable_here` is empty and `answer_card` gets `not_answerable_here`. OB-01 never counts `mcp`, so no gate opens, no L2 instruction is made and no consent is given. An answer given over MCP is not saved as a Decision for reuse (BQ-MCP-6). | api; outbox | 10.4, OB-01, FR-AGT-07 |
| MC-10 | **`start_run` is intake only.** It runs the same safety screen, brief, questions and approaches as a web request. The world's first `world.requested` has channel `mcp`, which is never an owner instruction. The person answers the questions and approves an approach in Tilo; nothing over MCP spends past intake. The per-person caps (SEC-16) apply, plus `start_run_per_day`. | api | FR-INT-01..05, SEC-16 |
| MC-11 | **Limits.** Per grant: 60 calls a minute and 10 writes a minute. Per person: 5 `start_run` calls a day, plus the SEC-16 per-uid limiter shared with the web. Over a limit the answer is `rate_limited`, and over a spend cap it is `over_cap`. Results are capped as the schema says. | api | SEC-10, SEC-16 |
| MC-12 | **Every call is audited.** Each authenticated call, refused ones included, writes one `mcp.called` to the person's Desk world, with `authz` equal to the authz of the grant's `mcp.granted`. Its data holds the grant, the client, the tool, the outcome, the refusal code and the ids touched, never argument text, content or a token. Granting and revoking write `mcp.granted` and `mcp.revoked`. An unauthenticated call has no person and no world, so it is counted only in the log. | api | SEC-11, HR-7 |
