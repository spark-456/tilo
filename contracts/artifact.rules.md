# Artifact store rules beyond the schema (artifact.schema.json v1)

ADR-0018, FR-MEM-12 (`docs/prd-supplement-2026-10-05.md`); 1.1.0 adds the `fetch` origin (ADR-0029, AR-09); 1.2.0 adds a writer unit's website HTML (ADR-0050, AR-10). `artifact.schema.json` checks one
`ArtifactVersion` record and one manifest revision. The store (`tilo_memory.artifacts`, P7) holds
the rules below on every call, and its tests cover them; a rule that needs the bytes, other
versions or the run cannot have an invalid fixture (AR-03 has a cross-reference case in
`fixtures/artifact/crossref/`). The generated pydantic models drop the schema's conditional
rules, so the store validates every record against the JSON Schema itself. Rule ids are stable.

| Rule | Rule | Checked by | Source |
| --- | --- | --- | --- |
| AR-01 | `content_sha256` is the SHA-256 of the stored bytes. Every `read` recomputes it; a mismatch raises `ArtifactCorrupt`, emits `alert.raised` and is never served or delivered. | store | 13.2, HR-1 |
| AR-02 | Versions of an id run 1, 2, 3 with no gaps; a record or blob is never rewritten. `parents` is empty for version 1 and otherwise names one earlier version of the same id; a restore's `parents` is the version it copies (schema: at most one). A restore copies that version's bytes, `media_type`, `sources`, `screening`, `screened_at` and `redacted`. | store (schema for the count) | 13.2, 13.4, FR-MEM-06 |
| AR-03 | Every call is scoped by `Scope(org_id, world_id, owner)` from the run, never a request: ids match `common.schema.json` patterns whole (no `/`, no trailing newline) before a blob key or archive path is derived, and a version of another org, world or owner reads as absent, so no call reveals that it exists. Every `sources[].archive_ref` names a raw-archive record of a run of the record's own org and world: for a unit, render or fetch output, the record's own `run_id`; a restore copies the copied version's `sources` and adds none; an upload has none (schema). The store refuses a put otherwise, and every archive read behind the Verifier's `load` goes through the version's Scope, so another world's record reads as absent. | store (schema for id shapes and upload sources; crossref case for the run) | 15.1, 16.2, 16.5 |
| AR-04 | Kinds and caps, checked before hashing. A unit's output (model-written) is text or JSON only (`text/markdown`, `text/csv`, `application/json`), never a file; tilo-render makes only files (PDF, PPTX, DOCX, XLSX, PNG, JPEG); an upload may be any of the nine; a fetch keeps only those six file types (AR-09); a restore keeps the copied type (schema, except restore). Content is at least 1 byte (text not whitespace only); text and JSON at most 2,000,000 bytes and files at most 50,000,000 (schema); a unit at most 10 outputs (schema: key index 0 to 9); a world at most 200,000,000 bytes. Breaking one fails the unit (FR-AGT-13). | store (schema for kinds, size and index) | ADR-0018 1, BQ-257 |
| AR-05 | One version per idempotency key `<run_id>:<unit_id>:<attempt>:<index>`: its run and unit equal the record's `run_id` and `origin.unit`, and a restarted unit (FR-AGT-10) gets the same version back. A fetch's index is `f0` to `f9` (its position among the unit's fetched files), a unit or render output's `0` to `9`, so the two never share a key (schema). The lookup is inside the Scope: a key of another org or world reads as absent, so a key never returns another world's version. Unit, render and fetch outputs have a key, uploads and restores have none (schema). | store (schema for presence and shape) | FR-AGT-10 |
| AR-06 | Each manifest revision passes `manifest.schema.json` and MF-01 to MF-06, names this version and carries its `content_sha256`. Revisions are append-only, `n` from 1 with no gaps (`created`, `reviewed`, `sent`, `exported`); readers take the latest. `cause` is the version's `artifact.created` or null for `created`, its `artifact.reviewed` for `reviewed` and the `data.transfer` out for `sent` (schema: neither of the last two null). `sources[].id` are unique and name sources of the manifest. The record's `sources` never leave Tilo: routes, exports and run bundles drop them (the manifest's `sources` are the exported trail). | store (schema for the shape and the non-null causes) | 12.4, 13.3, 16.2, FR-CON-10 |
| AR-07 | Text and JSON pass the secret redactor before put and the stored bytes are its output (`redacted` true when it changed them, BQ-258); a redactor error fails the put and nothing is stored. The redactor does not read files, so `redacted` false on a file means it did not run; SEC-01's secret scan of stores covers every stored version, files included. The store sets `screening` only from the SafetyProvider verdict on those exact stored bytes (PRD 16.3 item 2), with `screened_at` the verdict's time; a missing verdict (provider error, timeout, not run) is `unscreened` with `screened_at` null, never `clean` (schema). The check point for leaving Tilo is the policy engine: for any action whose `item` is an artifact version, the `safety_flag` tier modifier (PRD 10.4) is on unless that version's record, read from the store by the item's `artifact_id` and `version` (one source, never a caller's flag), says `clean`. So a `flagged` or `unscreened` version leaves Tilo only as T3, with a person (BQ-264). | store; policy engine (schema for `screened_at`) | 10.4, 16.1, 16.3, SEC-01 |
| AR-08 | Retention entity `artifact`, 90 days (PRD 15.1), `user_id` is `owner`. A delete removes every blob generation, the record and its manifests. | store (retention adapter) | 15.1, FR-MEM-09 |
| AR-09 | A `fetch` version is a file a unit's worker agent downloaded through tilo-browser's fetch (LW-08) for a `fetch_url` call; the store sets `origin` (unit and agent) from the run, never the runner. Its media type is set by code from the file's leading bytes: one of PDF, PNG, JPEG, DOCX, PPTX or XLSX (the Office types by their ZIP container and its main part), never HTML, SVG, a bare archive or a program, and never from the URL, its extension, a Content-Type header or a model; anything else is refused before hashing (schema for the six types). `sources` holds exactly one entry, the fetch's own raw-archive record of the same run, whose payload's `source.ref` is the cleaned URL (BQ-101, BQ-104) (schema for the count, AR-03 for the run). The bytes are screened like an upload (AR-07). The version reaches only its owner, through the owner-scoped content route; every path that sends or shares a file is already T3 (`attachments`, `share_file`, `external_sharing`), and Tilo never republishes a fetched file (BQ-LW-5). | store; tilo-browser; policy engine (schema for the kind, types, key form and source count) | 12.3, 13.2, 16.2, FR-CON-10; ADR-0029 8 |
| AR-10 | A `text/html` version is a website: one self-contained HTML file a `writer` unit made for a deliverable of format `website` made natively (origin `unit`, `website.rules.md` WS-01), at most 524,288 bytes (schema). AR-04's unit kinds gain `text/html` for this case only; an upload, a fetch or a render never stores HTML (schema), and a restore copies a stored website's type. HTML is text for AR-07: it passes the secret redactor and is screened. The store's put runs the WS-02 to WS-08 checker on the exact bytes it keeps, after the redactor, for every `text/html` version, and refuses a failing one before hashing (WS-09), so no path stores unchecked HTML. The version is served only as WS-10 to WS-13 say: a sandboxed preview with no network, or an attachment download. | store; harness (schema for the origin and the size) | 12.4, 16.2; ADR-0050 |

Events: `artifact.created` is written only after the store committed bytes and record, with
`content_sha256`, `media_type` and `size_bytes` copied from the record (`artifact.created` data
1.1.0), and every artifact event names a version the world recorded (event rule EV-15).
